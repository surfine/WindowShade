# 1.0.17 发布关 runbook（第一个 Developer ID 版）

用途：把 1.0.17 从"候选源码"推到"可发布"。门内全过 → 走文末「发布日流程」；任何一项 inconclusive / fail → 停，按本项目惯例记档。格式沿用 [1.0.16 runbook](v1.0.16-release-gate.md)。

**这一版特殊在三处**（2026-10-17 候选源码已备好，见各处 TODO）：

1. **换证书的一版。** 1.0.16 及以前是开发证书签的（Team `FVGLY6W6S4`），1.0.17 用 Developer ID（Team `DQ45KFVHJ8`），DR 一定不同。自动更新跨不过去，所以 appcast 那一项标了 `sparkle:informationalUpdate`（`belowVersion=17`）：1.0.16 只弹提示、给下载页（[docs/update.md](../update.md)「换证书的一版」）。发布关第 3 步改核「Developer ID、Team 是 `DQ45KFVHJ8`」。
2. **最低系统 macOS 15。** `Info.plist` 的 `LSMinimumSystemVersion` 早已是 15.0，appcast 这一项是 `15.0.0`（1.0.16 那项保持 `14.0.0`，留在 macOS 14 的人停在 1.0.16）。
3. **公证。** `./build.sh --release`＋`bash scripts/notarize.sh`；README 与官网里"还没公证"那句已删。

候选源码里已完成（本 runbook 之前）：`CFBundleShortVersionString 1.0.17`／`CFBundleVersion 17`；appcast 的 1.0.17 条目草稿放在 [appcast-item-1.0.17.xml](appcast-item-1.0.17.xml)（url、length、`edSignature` 写着 TODO；**故意不放进 `site/public/appcast.xml`**——线上清单带着 TODO 和旧签名块会让 1.0.16 的更新检查失败，所以 build 17 照样 PASS）；三份 README 与官网（中、繁、英）改 macOS 15、已公证、从 1.0.16 升级要手动下载一次；发布说明草稿 [v1.0.17.md](v1.0.17.md)。**没做**：构建、签名、公证、打标签、发布。

**顺序纪律：** 三份 README 与官网已写"已公证、macOS 15"，1.0.16 并不成立（开发证书签、未公证、支持 macOS 14）。所以这批候选源码**不要先合进 `main`、不要先部署站点**；README／官网／appcast 随 1.0.17 的 zip 上传到 GitHub Release 之后一起上线（发布日流程第 3 步），之前站点任何文案修改都从不含这批的提交出。

## Phase 0 · 建发布候选并过包级门禁（约 20 分钟）

先决条件：本人的钥匙串里有 Developer ID Application 证书（Team `DQ45KFVHJ8`），`xcrun notarytool store-credentials windowshade-notary …` 已存过凭证（见 DEVELOPMENT.md 第 3 步）。

```sh
git worktree add /tmp/ws-b17 <要发布的提交>        # 标签=源码=包：必须是已提交的干净检出
cd /tmp/ws-b17
bash scripts/check-release-version.sh                # 必须 PASS（build 17 > appcast 已发过的 16）
cd prototype
./build.sh --stage                                   # 开发证书隔离构建，先验：更新器接齐、--self-check 过
./build.sh --release                                 # Developer ID 签名，产物 ../.build/release/WindowShade.app
cd .. && bash scripts/notarize.sh                    # 送公证、钉票据、Gatekeeper 核
cd prototype && mkdir -p dist
VERSION=$(/usr/libexec/PlistBuddy -c "Print CFBundleShortVersionString" Info.plist)
ditto -c -k --sequesterRsrc --keepParent ../.build/release/WindowShade.app "dist/WindowShade-v${VERSION}.zip"
(cd dist && shasum -a 256 "WindowShade-v${VERSION}.zip" > "WindowShade-v${VERSION}.zip.sha256")
```

记下 zip 大小与 sha256：这就是要发布的数字。

### 包级门禁（`scripts/release-gate.sh`，换证书的一版要带 `--cert-change`）

先把草稿条目插进 `site/public/appcast.xml`（放在 1.0.16 条目前）并把 TODO 填完（url、`length` = zip 的字节数、`sparkle:edSignature` 用 `sign_update` 签 zip；然后重新签整份清单），再跑：

```sh
bash scripts/release-gate.sh prototype/dist/WindowShade-v1.0.17.zip --cert-change DQ45KFVHJ8
```

默认会用 `gh` 下载 v1.0.16 的 zip 当"上一版"（要联网、`gh` 已登录）。与 1.0.16 的差别只有一处：

| 步骤 | 1.0.16 | 1.0.17 |
| --- | --- | --- |
| 3 DR | 与上一版逐字相同 | **`--cert-change DQ45KFVHJ8`**：核 `Authority` 是 `Developer ID Application:`、`TeamIdentifier` 是 `DQ45KFVHJ8`；不比上一版的 DR |
| 7c | 无 | 清单里这一项是 `informationalUpdate` |
| 6 | 最低系统 14.0 | `LSMinimumSystemVersion` 15.0 = 清单 `15.0.0` |
| 9 | 跳过 | 仍要做：新版 `--self-check --write-sample-state <目录>`，1.0.16 的 `--self-check --read-state <目录>` 返回 0（上一版看得懂这一版的状态；脚本里这一步的结果如实记） |

另外手动核两件事，记进证据目录：`spctl -a -vv -t exec <App>` 显示 `source=Notarized Developer ID`；`xcrun stapler validate <App>` 通过。之后各版回到"DR 与上一版逐字相同"，不再带 `--cert-change`。

## Phase 1 · 核心窗口路径（真机，约 20 分钟）

同 [1.0.16 runbook](v1.0.16-release-gate.md) 的 Phase 1，对象换成 Developer ID 的新包（用 `open -a` 路线启动，别用 shell 直启；跑前 `lsappinfo front` 是 loginwindow 就先解锁）：单文档收起／展开、**同 App 两文档**、菜单栏路径、浅色与深色。

**这一版加验**：
1. **重新授权。** 新签名是新身份：辅助功能和屏幕录制都要重新打开；没授权时欢迎流程把这两项说清楚，授权后不用重启也能用。
2. **从公证包首次打开不被拦**（把 zip 经浏览器下载一次再解压，带隔离标记，双击打开）。
3. 本批新功能各看一眼：设置 → 高级 → 关于（导出诊断、导出／导入设置）、关掉计算器的卷帘条后 App 随之退出、音量亮度"改回用系统的提示"开关。

每个动作：截图 + 备注时间；说不清就记 inconclusive，不许猜成 PASS。

## Phase 2 · macOS 15 与 26 虚拟机回归（约 15 分钟）

最低支持系统是 15，发版前在另外两个支持版本的虚拟机里跑核心探针（规格已定：Aaron 2026-10-16）。VM 的搭法、账号、授权见 [DEVELOPMENT.md](../../DEVELOPMENT.md)「发版前的虚拟机回归」一节（外置 QA 盘上的 `wsqa-manual` 是 macOS 26.6.2，`wsqa-15` 是 15.6.1，先用 `./lume.sh run <名字> --storage windowshade-qa --display none` 开机）。

```sh
cd prototype && ./build.sh --stage                   # VM 回归用开发证书包（同源）；Developer ID 包另在真机验
cd .. && tests/vm/run-core-probes.sh lume@<wsqa-15 的地址>   # macOS 15.6.1
tests/vm/run-core-probes.sh lume@<wsqa-manual 的地址>        # macOS 26.6.2
```

通过条件：两台各六组全过。首次已有基线：2026-10-16，macOS 26.6.2 前五组全过、browser-more 三次里一次全过（记 inconclusive）；macOS 15.6.1 六组全过。这次的计时与基线相近（第一次画面变化约 170 ms、卷帘条约 390 ms）；明显更慢要记下来，不当作 PASS。VM 不能代替真实硬件矩阵，本关不写"硬件矩阵通过"。

## Phase 3 · 更新器（约 15 分钟）

- 在装着 1.0.16 的机器上，指向包含 1.0.17 条目的本地或预发布 appcast：应弹出"这一版要手动下载"的提示和**打开下载页**按钮，**不**尝试一键安装。
- 在 1.0.17 上点"检查更新"：显示已是最新，不崩溃、不弹假版本。
- 设置里不应出现"回到 1.0.16"（没有自动安装过，没有备份）。

## Phase 4 · 判定与记录（约 5 分钟）

通过条件：Phase 0 门禁全 PASS（含 `--cert-change`、公证核对）＋ Phase 1 全 PASS（含同 App 两文档）＋ Phase 2 两台 VM 各六组过 ＋ Phase 3 行为如上。证据落 `.build/release-acceptance-<日期>/`，每条一张表：场景 / 期望 / 实际 / 证据 / 判读（pass／inconclusive／fail）。

## 发布日流程（门过后；Aaron 点头、Aaron 按发布）

1. 冻结 zip ＋ `.sha256` ＋ 证据目录。
2. `sign_update` 签 zip，把 [草稿条目](appcast-item-1.0.17.xml) 插进 appcast 并填 1.0.17 的 url／length／`edSignature`，改 `pubDate`，**重新签整份清单**；`bash scripts/check-release-version.sh` 此时应失败（build 17 已在清单里）——这是预期，说明清单已含这一版；`release-gate.sh` 的 6、7b、7c 靠它通过。
3. 站点：`cd site && npm run build && npm run check`；**先上传包、后发清单**。
4. `git tag v1.0.17`（指向 Phase 0 的提交）→ `gh release create v1.0.17 … --notes-file docs/releases/v1.0.17.md` → 上传 zip 与 `.sha256` → 下载回来核对哈希。
5. 更新下载大小的数字：README 三份"1.0.16 download"那一行改成 1.0.17 的实际大小；官网 `site/scripts/content.mjs` 里的 `facts`（中、英两处 `1.0.16 · ZIP 9.83 MB`）和 `zh-hant.json` 对应项；`notchIntro` 里"1.0.16 候选功能，尚未发布"的措辞按当时实际状态改。
6. `docs/releases/v1.0.17.md` 去掉草稿说明；`docs/releases/README.md` 的"已发布"表补一行。
7. 可选：先 beta 频道自用一天；分批推送见 DEVELOPMENT.md 对应节。
