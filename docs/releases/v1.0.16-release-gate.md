# 1.0.16 发布关 runbook（真机，60–90 分钟）

用途：把 1.0.16 从"候选"推到"可发布"。门内全过 → 走文末「发布日流程」；任何一项 inconclusive/fail → 停，按本项目惯例记档。

**为什么不是直接用旧候选 ZIP（4fe6518e）**：其构建源是 2026-10-10 的未提交工作树，与任何提交都对不上（对照 `source-manifest.json` 逐文件核对：与「第二十二波」提交差少数文件，与当前 main 差更多）；其包内主程序二进制（sha256 前缀 `9567012c`）与此前真机探针所用的 staged 二进制（`91762d1d`）**不是同一个**。用旧包发布等于"验过的包 ≠ 发布的包"。因此本关的基线是从提交重建的新候选——做到**标签=源码=包=证据**四者一致。全部旧证据继续留档，但真机门本来就得在新包上补。

## Phase 0 · 建发布候选并过包级门禁（约 15 分钟）

基线提交二选一：

- **0-A（推荐）：`e4db602`（第二十二波快照，含两处崩溃修复；与新 main 的差异文件可在 `git diff e4db602 HEAD` 里自行核对）** —— 1.0.16 的范围与现有发布说明草稿一致；英文半迁移与第 26 批动效衔接留给 1.0.17。
- 0-B：当前 `main`（HEAD）——会带上第 23–27 批（英文适配首批：仅设置外壳+卷帘页+高级页，且有两个已记录小问题）。若选它，Phase 1 里加验两条：设置里切换语言立即生效且停在当前页；卷帘页滑杆读数位置正常。否则不要选它。

命令（干净检出 + 构建；需 Xcode/Metal 与签名证书，见 DEVELOPMENT.md）：

```sh
git worktree add /tmp/ws-b16 e4db602          # 或 HEAD
cd /tmp/ws-b16/prototype
WINDOWSHADE_CODESIGN_IDENTITY="Apple Development: …" ./build.sh --stage
# 产出 dist/WindowShade-v1.0.16.zip 与 .sha256 —— 记下大小与 sha256，这就是要发布的数字
```

包级门禁 = DEVELOPMENT.md「发布关」§4 的 9 步（deep-strict / DR 与 1.0.15 逐字一致 / `--self-check` 含 `build=16` / CFBundleVersion>15 / LSMinimumSystemVersion / lipo 架构 / Sparkle 键与 UpdateGuard / 首个更新器版跳过"上版读状态"）。一条条跑，结果记进证据目录。

启动候选（供 Phase 1–3 用；shell 直启会丢 AX 授权，用已验证过的路线）：

```sh
open -a /tmp/ws-b16/prototype/dist/…（或解压出的 WindowShade.app）--args   # open 路线：责任人=自身，继承日常版 TCC
# 跑前守卫：lsappinfo front 是 loginwindow 就先解锁
```

## Phase 1 · 核心窗口路径（约 20 分钟）← 门里最重要，历史雷在这

用一个专用测试文档（不要动你自己的文档）：

1. **单文档**：双击标题栏收起 → 看到卷帘条（预期：首变 ~165ms、条 ~415ms；以实际截图为准）→ 双击卷帘条 → 原样恢复。
2. **同 App 两文档**（历史缺陷"两文档时收起不出卷帘条"，当前源码从未复现过——**门内最关键的一条**）：同一文本编辑器开 A、B 两份 → 对 A 双击标题栏 → 看卷帘条是否出现 → 双击恢复 → 对 B 重复。
3. **菜单栏路径**：菜单里对当前窗口收起/展开，行为与双击一致。
4. **外观**：浅色、深色各做一次第 1 条；"收起后的样子"两档（跟原来一样 / 统一标题栏）各看一眼。
5. 每个动作：截图 + 备注时间；看不到、说不清 → 直接记 inconclusive，不许猜成 PASS。

## Phase 2 · 欢迎三步（约 10 分钟）

- 走一遍首次启动：说用途 → 之前常用哪个系统 → 两项授权（辅助功能、屏幕录制）。开着"减少动态效果"时应不动动画。
- 菜单「欢迎使用 WindowShade…」随时能重开。
- 试用入口/默认值细节见 `v1.0.16-defaults.md`。

## Phase 3 · 更新器（约 10 分钟）← 1.0.16 是首个带 Sparkle 的公开版

- 包内已核：`SUFeedURL = https://windowshade.aaronlau.me/appcast.xml`、`SUPublicEDKey` 正确、UpdateGuard 同 Team。
- 线上 appcast 尚未部署（本来就是发布日先上）。门内做简验：打开更新菜单/点"检查更新"——**不崩溃、不弹假版本**；feed 缺失时的实际表现如实记录（不猜测 Sparkle 行为）。
- 完整更新验证在发布日（见下）。

## Phase 4 · 判定与记录（约 5 分钟）

- 门的通过条件：Phase 1 全部 PASS（含同 App 两文档）+ Phase 2 全过 + Phase 3 简验无双异常。
- 证据落 `.build/release-acceptance-20261012/`，每条一张表：场景 / 期望 / 实际 / 证据（截图名）/ 判读（pass/inconclusive/fail）。截图按 `场景-顺序.png` 命名。
- 全过后把结果给我，我按发布日流程收尾。

## 发布日流程（门过后执行；照 DEVELOPMENT.md §4–§8）

1. 冻结新 ZIP + `.sha256` + 证据目录（source 清单、包级门禁输出、本 runbook 结果）。
2. `sign_update` 签 ZIP → 在 `site/public/appcast.xml` 建/加 1.0.16 条目（保留最近三条，写法见 `docs/update.md`）→ 站点 build/check → 部署（先上传包、后发清单）。
3. GitHub Release：`git tag v1.0.16`（指 Phase 0 的基线提交）→ `gh release create ... --notes-file docs/releases/v1.0.16.md`（去掉草稿标记）→ 上传 ZIP 与 `.sha256` → 下载回来核对哈希。
4. 更新 README 双版下载数字（1.0.16 实际大小）。
5. 可选但建议：先发 beta 频道自用一天，再去掉频道标记（DEVELOPMENT.md §7）；分批推送 `phasedRolloutInterval`（§8）。

## 门内不做、发布后 beta 项（如实写进发布说明/回执）

真机安装升级一部、日常使用一天、硬件矩阵、H07/H08、CarPlay 真人手指长按（上轮 inconclusive）、120Hz、真手感清单、shelf-glance（已定案为 macOS 27 能力缺口，随系统更新复查）。
