# 修缺陷的顺序

目标：从看到一个问题到确认修好，用的时间最短，而且留下的证据别人能复核。
每层测什么、什么时候跑，见 [testing.md](testing.md)。这份文件只管顺序、等待和决定。

## 1. 一次往返花在哪里

本机实测（2026-11-02，Mac Studio，M 系列）：

| 步骤 | 一次的成本 | 对策 |
|---|---|---|
| `build.sh --check` | 约 5 分钟 | 用 `scripts/local-gate.sh check`，结果写进 `.build/gate/` |
| 单个单元脚本 | 1–10 秒 | 改动集中时 `--only <关键字>`，别全量 |
| 全量单元（200 多个，6 路并行） | 5–8 分钟 | 推送前跑；不要每改一行跑一次 |
| AppKit 套件 | 1–3 分钟 | 改窗口/设置界面时跑 |
| 虚拟机核心探针 | 10–90 分钟 | 每周和发版前跑，不用来确认单次修复 |

没有托管 CI 之后，**等待时间不再是排队，而是自己愿不愿意等**。所以规则更简单：
短回路（编译 + 相关单元）每次推送前跑，长回路（全量、AppKit、虚拟机）批量跑。

## 2. 修一个缺陷的顺序

1. **先看证据，再写代码。** 用户录像逐帧看，日志按时刻对上录像；说不清“哪一帧、哪一行日志”之前，不动代码。
2. **推测先在已有数据里查证。** 找支持或否定它的日志、帧、代码；找不到，就在同一次改动里加上能回答这个问题的日志，不为验证单独跑一轮。
3. **测试和修复放在同一次提交里。** 先写能复现缺陷的测试，再改代码；测试脚本要能被 `local-gate.sh unit` 发现，否则等于没写。
4. **不确定哪种做法有效时，一次把所有做法放进去**，用日志记下哪一种生效；下一轮只保留生效的那种。
5. **改完先跑短回路**：`scripts/local-gate.sh unit --only <相关关键字>`，通过再跑 `check`。两项都过再推。
6. **推送后立刻做下一件事**，不空等长回路；长回路结果出来再决定要不要回滚。
7. **不打断正在跑的检查。** 新改动先在本地累积，结果出来后再一起推。

## 3. 什么时候问用户

- **不问**：有明显更好的做法时，直接做，事后一句话说明做了什么、为什么。技术取舍（等多久、用哪个接口、先修哪个）都属于这一类。
- **只在两种情况下问**：
  1. 需要用户本人动手：授权、录屏、在他的机器上操作。写明步骤，不写“要不要”。
  2. 产品上的取舍，而且两种做法用户都可能要。写明决定和代价；用户不同意再改。
- 不写“要的话告诉我”“你看要不要”这类句子。

## 4. 汇报

每次只写三样：结果、下一次结果的时刻、用户要做的事（没有就不写）。
修好的写“已修复”并给出依据（测试名、提交号、证据路径）；没修好的写原因和下一步，不写过程。

## 5. 已知失败

只在特定机器或虚拟机上出现、已决定暂不修的问题，登记在 [known-failures.md](known-failures.md)，
报告时一句带过。登记不是豁免：每一项都要写“下次什么时候再看”，到期没有结论就重新评估。
