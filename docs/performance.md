# 性能：实测量级、已走通的手法、已证伪的方向

本文只记**测过的数字**和**验证过的结论**，用来避免把同一条路重新走一遍。
测量环境：Mac17,4（Apple Silicon）· macOS 26.5 (25F71) · 2026-09。
换机器或换系统版本后数字会变，但相互之间的**量级关系**是结构性的。

## 一、调用成本的量级

用 `--duo-ax-bench` 从**签名后的 app bundle** 运行得到（它需要辅助功能权限，
未签名的测试二进制拿不到，AX 调用会直接返回而不发 IPC）：

| 操作 | 耗时 | 相对 |
| --- | --- | --- |
| SkyLight 查询（走 WindowServer，不经 App） | 0.013ms | 1× |
| AX 单个属性读（位置 / 尺寸 / 标题 / 角色）**，目标 App 空闲时** | 0.0–0.1ms | ~8× |
| 同上，**目标 App 正忙时**（例如刚被要求隐藏自己） | **约 19ms** | ~1500× |
| CGWindowList **全量**枚举（所有 App 所有窗口） | 3.3ms | ~250× |
| **AX 取单个 App 的窗口列表**（`kAXWindowsAttribute`） | **18–25ms** | **~1500×** |

两条反直觉的结论，都直接决定了优化方向：

0. **同一个调用的成本取决于对方忙不忙。** 上表第二行和第三行是同一个
   `axPosition`：目标 App 空闲时 0.1ms，正忙时 19ms，差 190 倍。批量折叠时
   我们刚要求一批 App 隐藏自己，它们全都处在最忙的状态——**在那之后对它们做
   任何 AX 调用都要按「忙」的价格算**。据此定下的规矩：能在批量操作开始前
   做的读取，全部提前到预热阶段并发做完（那时 App 还空闲）。

1. **AX 本身不慢，慢的是「要一份列表」。** 单属性读 0.1ms，可以随便调；
   而 `kAXWindowsAttribute` 一次就 20ms，比把全系统窗口列一遍还贵 6 倍。
   `kAXChildrenAttribute`（工具栏探测、红绿灯几何用它）是同一个量级。
   **优化的单位是「减少列表枚举的次数」，不是「减少 AX 调用的次数」。**
2. **时间花在等，不在算。** 上面所有耗时都是 IPC 往返和目标 App 的 runloop
   响应时间，与本机 CPU 快慢基本无关——所以 M1 上不会明显更慢，M5 上也不会
   明显更快。用「换更快的机器」来解释或解决这里的性能问题是错的。

其它实测常数：

| 项目 | 耗时 |
| --- | --- |
| Metal 管线创建（`makeRenderPipelineState` ×3 + 载入 metallib） | 首次 69ms，之后 0.4ms（Metal 内部有管线缓存） |
| 快速预览截图 `CGWindowListCreateImage` | 约 35ms/窗口 |
| 桌面效果会话创建 + 流启动 + 显示 + 销毁 | 合计 150–220ms，其中无任何主线程阻塞 > 50ms |
| **目标 App 执行 app-hide / minimize** | **19–474ms/窗口** |

最后一项是折叠路径的**地板**。它是别的进程在响应我们的请求，方差极大：
Ghostty 之类几毫秒就回，Safari 在排版、转码类 App 在忙时能拖到几百毫秒。
同一份代码折叠 8 个窗口可能是 184ms，折叠 11 个可能是 2131ms，差别几乎全在这里。
**报「提速多少倍」时必须说清窗口构成，否则数字没有意义。**

## 二、已证伪：用 SkyLight 绕开目标 App

**结论：在 SIP 开启的系统上不可行，不要再尝试。**

思路是合理的——`SLSSetWindowAlpha` 把窗口 alpha 归零、或 `SLSMoveWindowWithGroup`
把窗口挪到屏外，请求直接到 WindowServer（0.013ms），完全不经过目标 App 的
runloop，可以绕开上面那个 19–474ms 的地板。

实测结果：**调用返回成功，但回读发现值没变。**

```
private SLS alpha did not apply id=7806 pid=744 current=1.00
private SLS offscreen did not park id=227 pid=715 reason=fallback
```

15 次尝试，15 次如此。**跨进程的 SkyLight 窗口改动在 SIP 开启时被静默丢弃**
（yabai 需要部分关闭 SIP 正是为此）。这不是 API 用法问题，是权限边界。

要让它生效只能让用户关掉 SIP，而正常用户不会为了折叠快一点去关 SIP，所以
这条路被永久排除。曾经加过的「快速隐藏」实验开关已删除（见 `197b1f7`）：
留一个必须关 SIP 才生效的开关，只会让人打开、看不到变化、然后以为是自己
配置错了。

`privateSLSAlphaHide` 仍留在 `fallbackHide` 的**最后一环**（万一环境允许），
但带一次性探测：首次确认无效后本会话不再重试，不必每个窗口都白付一次
写入 + 一次回读。

## 三、已走通的手法

按收益排序。共同前提是：**先测再改**——这一轮里有两次「凭直觉的优化」反而
让代码变慢（见第四节）。

**1. 用 CGWindowList 筛掉注定为空的 AX 枚举。**
专注模式原本遍历全部运行中的 App 并对每个调用 `appWindows(pid:)`。实测 84 个
候选进程里只有 22 个拥有窗口——另外 62 个只可能返回空数组，却各要付一次
同步 AX 往返（最坏卡满 2s 消息超时）。判据是可证明安全的：**没有任何
CoreGraphics 窗口的进程，不可能有 AX 窗口**。发现阶段因此从约 8 秒降到
200ms 以内。启动时的救援扫描原本有同样的循环，且连 activationPolicy 都不筛。

**2. 并发做只读的 AX 工作。**
AX API 可在任意线程调用。各 App / 各窗口之间没有依赖的只读工作都可以
`DispatchQueue.concurrentPerform`，总耗时从「求和」变成「最慢的那一个」：

- 窗口枚举（`concurrentAppWindows`）
- 外框画像解析（`ChromeProfileCache.prewarm`）——980ms → 0ms
- 快速预览截图（`concurrentQuickPreviews`）——串行 70ms → 并发 41ms（2 窗口）

写入侧不能这么做：建 overlay 是 AppKit、改 `shaded` 字典是共享状态，都必须
留在主线程串行。**并发只用在「读」上，是这一节全部收益的边界。**

预热缓存时注意：`ChromeProfileCache.entries` 没有锁，所以是**后台并发算、
回主线程一次性写**，保持「只在主线程读写」这个前提不变。

**3. 事务级备忘，而不是 TTL 缓存。**
一次折叠里同一个 App 的窗口列表会被要三四遍（刷新元素、找焦点继承者、
数窗口数决定隐藏策略），而事务内它不可能变。`appWindows` 因此支持一个
**显式开启的备忘作用域**：`shade` / `unshade` 进入时开启，退出即丢弃。
每窗口枚举次数从 3.6 次降到 1.3 次。

刻意不用 TTL 缓存：那种缓存会在「App 在 unhide 后重建了 AX 元素」这种
场景下悄悄返回陈旧元素，而这恰恰是恢复阶梯存在的理由。

**4. 判断元素是否可用，要用存活探测，不要用几何匹配。** 见第四节。

**5. 窗口动画要成组，不要串行。**
`NSWindow.setFrame(_:display:animate:)` **会阻塞调用方直到自己那段动画播完**。
放在循环里逐个调用，总耗时就是各自动画时长之和——9 条卷帘条归位实测 3201ms，
而且用户看到的是它们一条接一条地挪。改成一个 `NSAnimationContext` 组、用
`animator()` 代理，所有窗口同时动，总耗时收敛到一段动画，降到 200ms 以内。

注意：动画期间 `window.frame` 是中间值。紧接着要读最终位置的调用方
（展开真窗口时要按卷帘条位置定位）必须走不带动画的分支。

**6. 主线程上的长任务要分帧。**
折叠 N 个窗口是线性成本，躲不掉；但可以不一次性占住主线程。按**时间预算**
推进（每轮 runloop 折到 120ms 用完就让出，下一轮继续），总时长基本不变，
但菜单栏和输入不再被整段冻结——十几个窗口时这是「卡住了」和「正在进行」
的区别。首帧阻塞从 3434ms 降到 291–495ms。

会话建立等收尾动作仍然等全部折完后一次性完成，语义与同步版一致；级联
期间要拒绝新的同类请求（`focusCascadeActive`），否则两次操作会交叉修改
同一份状态。

**7. 别为了打日志付 IPC。**
`applyRestoredGeometry` 每次调用 4 次 AX IPC：2 次写 + **2 次回读**，而回读
的唯一用途是拼日志里的 `actual=(...)`，不参与任何判断。恢复阶梯每个窗口
跑 80/250/550/1100ms 四档，恢复 15 个窗口就是约 120 次纯为日志的往返。
现在只有首档、末档、以及写入报错时才回读。

**8. 空闲时不要跑 CADisplayLink。**
`FoldRenderer` 的 MTKView 是 `isPaused = true`，只有显式 `render()` 才绘制；
而设置窗口原本无条件挂一个 60fps 的 display link，窗口开着就一直每帧
`render()`，哪怕实时预览关着、画面一帧没变。改成只在实时预览真的在推帧时
才跑时钟，静态示意图在参数变化 / 切回页面 / 视图尺寸变化时各画一次
（MTKView 暂停后不会自己重画，尺寸变化要补一帧）。设置窗口空闲 CPU
从 2.0% 降到 0.6%。

同理，效果会话在等待首帧期间也在以 60fps 空转 `render()`，所以**首帧预算
不能给太长**：实测成功呈现的中位延迟 93ms，而原本的预算是 2s。批量折叠时
多个会话互抢还会形成「越慢越超时、越超时越慢」的正反馈。预算收到 0.5s，
并且批量操作期间直接不起这个效果（十几个卷帘动画同时播本来也看不出来）。

## 四、两次「凭直觉的优化」反而变慢

都是同一个错误：**拿几何匹配当身份校验。**

`windowID(of:)` 内部**优先**用位置 + 尺寸 + 标题去和 CGWindowList 比对
（`publicWindowID`），`_AXUIElementGetWindow` 只是它的兜底。于是：

- 在 `refreshedWindowElement` 里写 `windowID(of: fallback) == id` 做快速路径，
  看起来省掉一次枚举，实际上**级联折叠时窗口陆续被隐藏、CG 列表一直在变，
  几何匹配会失配**——每个窗口先付一次失败匹配、再付一次完整枚举。
  元素刷新从 39ms 涨到 612ms。
- 改成 `_AXUIElementGetWindow(fallback, &id) == id` 也不行：传进来的 `id`
  本身来自 `windowID(of:)`（几何匹配的结果），两者对某些 App 并不一致，
  比对**系统性失配**。元素刷新仍是 236ms。

正确做法是**不做身份比对**。调用方如果刚刚枚举出这个元素（专注模式在并发
发现阶段几毫秒前才拿到），它知道元素是新鲜的，只需确认还活着——一次
`axPosition` 属性读，0.1ms。元素真的死了，写入会失败，上层本来就会重新解析
后重写。元素刷新降到 1ms。

恢复路径上的 `resolvedWindowElement` 犯了同一个错（拿 `state.sourceWindowID`
比对），已一并改成存活探测。

## 五、诊断工具

**`--duo-ax-bench`**（只读）打印本文第一节那张表。必须用签名后的
`WindowShade.app/Contents/MacOS/WindowShade` 运行，未签名二进制没有辅助功能
权限，AX 调用会直接返回而不发 IPC，量不到真实延迟。

**卡顿归因。** `MainThreadStallSentinel` 用主 RunLoop observer 测量两次活动之间
的间隔，超过 0.5s 报一次。注意两点：

- 它量的是**两次 runloop 活动之间**，不是两条日志之间。主线程卡在一个长调用
  里时，app 照样能打日志——所以「日志连续」不等于「没卡」。
- 它在阻塞**结束后**才拿到控制权，光报时长无法定位。因此 `MainThreadActivity`
  记录主线程活动，报告时给出**卡顿窗口内累计占用最久的那个标记**及其次数与
  占比。早期版本报「最后结束的那个」，结果把恢复 15 个窗口的 8 秒记到
  `menu: 重建` 头上——几秒的连续忙碌通常由几十次短调用组成，末尾那次往往
  只是恰好排在最后。`占 0%` / `未标记` 本身也是信息：说明阻塞落在所有标记
  之外（多半在异步回调里）。

**`foldPhase` 分段报告。** `shade()` 内部各段累计，一次专注结束时一并报出
（单段只有几十毫秒，逐次打日志会淹掉日志）。定位未覆盖的时间用**二分**比
逐个加探针快：把整个安装闭包罩上，它与已知子项的差额直接指出剩余时间在
安装之内还是之外。

**门限日志的读法。** `logIfSlow(label, threshold:)` 只在超过阈值时记录，
所以**某一行没出现就是结论**——说明那一段已经快到阈值以内了。

## 六、改这一带代码时的注意事项

`tests/duo-integration-check.py` 有两条**源码顺序断言**，守卫崩溃一致性：

```
recordShadeRecoveryIntent(  必须出现在  let hide = hideWindow(  之前
let hideVerifiedNow = hideTookEffect(  必须出现在  didVerifyFold(  之前
```

给这两处加计时时**不要用闭包包装**——实际执行顺序不变，但守卫匹配的文本会
消失，测试会红。用手工计时（记起始时间、直接累加）保留那段文本原样。
