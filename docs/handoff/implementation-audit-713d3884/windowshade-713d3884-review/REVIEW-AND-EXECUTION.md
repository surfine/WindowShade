# WindowShade 实施复核与下一轮执行规格

日期：2026-10-05。审查快照：`713d3884e31d4d6e698a7dc81df99219db1518b3`，分支 `cursor/silent-effect-receipts`。同期 main 是 `b271fcf`。

这里的“现状”来自实际阅读的源码和已提交日志；“要求”“目标”“建议配置”是本次拟议规格，不是实测成绩。仓库和官方来源完整定位见 `sources.json`。

## 1. 实施判断

WSR-01 至 WSR-03 已经形成真实代码进展：模拟点头不再出现在生产确认入口；glance 调用真实预览并检查 isLive；cover 建立逐屏黑色不透明面板；恢复队列的 MainActor 隔离崩溃得到修复。现有一次性授权账本、旧窗口恢复、共用刘海、真实帧呈现和 Swift 6 并发检查应继续使用。[C01–C08]

WSR-04 至 WSR-06 仍不能标为完成。最新相机日志的 `camera=authorized` 后面是 `samples=0 faces=0 recognition=nil`，只证明该场景没有错误执行。手机观测是 inconclusive；系统解锁本轮没有准入。全部七条产品目标继续保留，不能把拒绝执行、显示占位文案或单元测试通过当作交付功能。[C02,C03,C09]

硬件矩阵 20 项中有 6 pass、8 partial、5 not_run、1 inconclusive，但 pass 中也混有纯逻辑与受限临时窗口测试，不能拿 6/20 推导产品完成百分比。8 秒 soak 退出成功仅检查错误与对象释放；没有帧率门槛，且其前十秒保持 progress=0.5，8 秒测试根本没有进入反转阶段。[C03,C10,C11]

### 需要保留、不要重新派为待实现的优化

- `EffectFrameSource` 的 latest-frame 槽、代次和有序 start/stop。
- `FoldRenderer` 的 CVMetalTextureCache、GPU 完成前资源保活、paused MTKView、dirty 渲染、960 像素宽光学中间层、GPU-only private 中间纹理。
- `FoldRenderer` 的 vImage 转换已经存在。问题是调用所在的主线程和复用边界。
- 音乐来源已有通知置脏和 30 秒补查，音频设备已有监听缓存，音效已有后台队列。
- 盖角已经有推送/看门狗/回退路径，不再安排“从零改成推送”。
- 恢复日志新增记录已经去掉标题，保留旧记录读取；仍需检查数值、旧数据迁移和隐私说明。[C07,C12–C17]

## 2. 先修四个直接影响可用性的缺口

### R01：恢复日志的其余数字仍能触发崩溃

文件：`prototype/Recovery/Journal.swift`、`prototype/Recovery/Rescue.swift`。

`journalID` 已经精确转换并拒绝布尔。但 `journalNumber` 仍接受非有限 NSNumber/Double，Rescue 又执行 `CGDirectDisplayID($0)`、`Int(target.x)`。负显示编号、超界整数或非有限坐标可能在恢复前或日志格式化时触发陷阱。[C07,C08]

修改合同：

1. 按字段做解析。显示编号使用精确非零 UInt32；坐标要求有限并保留合法负坐标；宽高有限且为正；alpha 有限且在允许域；日期要求有限且处理异常未来值。不能把所有负数都拒绝，已有停车点就是负数。
2. 对 UInt64 的 spaceID 不再经 Double 中转。新格式存精确整数；旧 Double 仅接受能无损验证的值，无法确认就记录未知，不截断。
3. 错误条目单独隔离，继续处理其他可恢复窗口。不要为获得干净 JSON 删除唯一恢复线索。
4. 日志格式化也不得陷阱；不要对未经校验的浮点做 Int 强转。
5. 调整 `rescueActionVerified` 时保留最终 AX/可见性/身份读回。安全解析不会替代效果验证。

验收：布尔、NaN、±Infinity、-1、0、1.5、UInt32.max、UInt32.max+1、巨大坐标、负停车坐标、损坏单条与正常多条混合；好条目仍恢复，坏条目保留为可检查状态。先跑本包的隔离示例，再把同类断言加到真实 Journal/Rescue 测试中。隔离示例不是自动替换脚本。

### R02：遮罩按显示器身份对账，能在别的 App 前台时退出

文件：`prototype/App/WS2SilentPrivacyCover.swift`，沿用原 App 的输入入口和显示器变更通知。

现有真实遮罩值得保留，但 `observation.requestedScreenCount` 来自 `panels.count`，可见数也是这批自建 panels；这证明面板可见，不证明当前所有显示器覆盖。没有热插拔重建；重复 cover 先 clear 再创建；Esc 仅 local monitor，非激活面板下按键可能仍发往外部前台 App。[C05,A08]

修改合同：

- 在 cover 意图发生时保存 expected display IDs、frame、缩放、epoch；观察按 ID、frame、可见性核对。未知显示器编号不能都折成 0。
- 覆盖有效期间监听显示器/模式改变，先处理新增或变化的显示器，更新当前期望集合与部分完成状态。热插拔之后补画存在不可消除的发现延迟，不宣称系统级隔离。
- 对现有显示器优先复用面板；不要重复请求就先撤下所有旧遮罩，避免人为增加空窗。
- 已有输入路由在方便遮挡生效时处理 Esc，覆盖本 App 与外部前台两种事件来源；无需长期新增全局键盘监听。刘海也提供明确的清除按钮。
- 方便遮挡允许退出。验证后显示的模式若加入，取消验证不得沿用方便遮挡的清除行为。两种策略明确分开。

验收：Safari/终端为前台时 Esc；双屏开启后插入第三屏、拔屏、缩放/镜像切换；重复请求；未知 displayID；锁屏/睡眠；退出后没有残留面板和监听。H07 从 partial 转为实际热插拔证据。

### R03：每个异步窗口动作都有终点，旧预览回调不得覆盖新命令

文件：`prototype/App/WS2SilentHost.swift`、`WS2SilentApply.swift`，既有 Glance、FoldCompletion、RestoreVerifier、PinnedPreview、SlideOver、PictureInPicture 的完成入口。[C04,C06]

现状：glance 用 50ms 短轮询等 isLive，但超时只结束 operation ledger，不更新 lastResult 或页面；先判 isLive 再判 Date 截止；同页提出下一条命令/部分取消入口没有统一撤销旧 watcher。折叠、展开、撤销返回 unknown；置顶启动回调被 `{ _ in }` 丢掉；侧拉和 PiP 也缺同等的终态连接。

修改合同：

1. 复用原 operation ledger 和已存在的 token/epoch。派发之前创建 operation，绑定命令、目标实例、revision、显示器、页呈现代次。
2. Glance 在对应会话的首帧真实可见时回调；只带 windowID 不够，要带采集/呈现代次，避免同一窗口旧会话冒领新动作。
3. 若回调暂时不能接通，短轮询只作有明确期限的迁移路径；使用项目单调时钟，先校验 deadline、epoch 和当前操作，再读取结果。
4. 所有取消、替换候选、关闭和挂起都撤销旧 UI 更新权。已执行的物理效果仍需要对账，不因 UI 取消被伪写为“没有执行”。
5. 终态事件只更新对应 operation。旧结果可留在其记录，不改当前新候选文案；超时必须更新该操作可见状态。
6. 折叠绑定 FoldCompletion 的已隐藏/真实效果；展开绑定真实窗口可见与恢复观察；置顶绑定首帧、面板和目标；侧拉/PiP 绑定最终几何/可见性。内部字典的移除不等于原窗口已经恢复。
7. “未知”作为诚实中间结果可以保留，但不能永久替代完成线路。

验收：A glance 等待→B 新命令→A 首帧；A 等待→取消→A 首帧；过期边界前后；同一窗口关闭重建；同一 id 新会话；置顶/折叠/展开各一次真实成功与一次受控失败。缺失首帧必须注入，正常收到四帧不能叫零帧路径测试。

### R04：相机要先拿到真实成功样本

文件：`prototype/App/FaceObservationSource.swift`、既有人脸观察/头部手势消费端、静音里程碑探针。

现状：最新日志 samples=0；生产源有 500ms 预热、8Hz 分析节流、采集时间过期过滤；Vision perform 的错误被 catch 后直接丢弃。许可成功不能区分是没有帧、帧被过滤、Vision 失败，还是消费者漏收。[C09,C18]

第一步只增加隐私安全的计数：captureReceived、warmupSkipped、throttled、invalidBuffer、clockConversionRejected、staleFrame、visionStarted、visionFailed、noFace、multipleFaces、delivered。按阶段记录时间和受控错误枚举，不写图像、特征、真实相机标识或无上限错误文本。

第二步在授权真机上做正向闭环：普通单脸连续10秒有效观察；主动做一次指定头部动作；对应低风险操作真实完成；点头之前旧候选不能执行；挑战头动不能顺带确认命令。再测遮挡、断流、换人和旧回调。没有获得正向样本时，不能宣称“头动已实现，只差攻击测试”。

第三步落实真正的人脸录入、同主体比对和头动/嘴部几何挑战。`VNDetectFaceLandmarksRequest` 只输出几何，不是身份证明或活体模型；不要把成功返回关键点写成脸匹配成功。模型权重、预处理、模板版本、许可证、阈值校准单独记录。屏幕补光保持可退出；安全阈值不因省电下调。

## 3. CPU、GPU、ANE 的具体优化

### CPU：先减少阻塞和无效工作

`FocusSession.startFocusCurrentAppSession` 在调用方同步等待多批 concurrentAppWindows、concurrentQuickPreviews、ChromeProfileCache.prewarm；“内部并发”不保证主线程在等待期间活着。`foldFrom` 仍按 focusFoldFrameBudget 分段，分段不能自动解除单次同步 IPC 阻塞。[C19]

把流程拆成已有事务的几个阶段：主线程快照身份/策略→有界后台只读发现与预处理→主线程核对目标与当前状态→短 UI 提交→异步观察回执。跨同一目标进程的工作有上限，不按窗口数量创建无界并发。AppKit 创建、焦点与原共享字典继续留在主线程。后台结果过期必须丢弃；不删除恢复日志写入屏障、不移除恢复读回、不靠关闭 SIP 换性能。

QoS 随任务用途设置：即时输入/短呈现用交互优先；用户刚触发的预览准备用 userInitiated；扫描、缓存和非紧急设备刷新用 utility。不要默认所有队列 userInteractive，也不手工锁定 P/E 核。计算很小的几何、余弦相似度和状态决策继续 CPU/Accelerate；小任务不值得来回创建 GPU 命令。[A04]

`FoldRenderer.texture(from:)` 的 vImage 已快于旧 CGContext，但仍从 MainActor 同步调用。将大图转换/纹理准备放在隔离 worker，UI 只交换已准备的资源并复核 revision。缓存依据包含 source、color profile、尺寸和 generation；取消不等待无用转换。缓存 ColorSpaceConverter/管线是数据路径优化，不能让旧图片冒充新一帧。

### GPU：现有架构可用，优先复用与节奏

保留 CVMetalTextureCache 和 GPU 生命周期保活、private 中间纹理、framebufferOnly、960px 光学层、原分辨率文字与前景合成。[C12,C13]

具体改变：

- `Duo.metal/duoPage` 只依赖源纹理和 content rect，不依赖 progress。相同 source generation/frame/content/color/texture revision 下，仅 progress 变化时不要重建全尺寸 page base 和 mipmap；只重做光学和合成。新源帧或裁切变化要失效缓存。失败提交也要失效，不能标为可用缓存。[C13,C20]
- `FoldRenderer` 将 busy 清除排回主线程；GPU 完成与主线程收到完成之间的时间单独记账。保持单在途作为基线，对比受控双在途，不盲目增加 queueDepth 或 drawableCount。双在途需要每帧保活与独立可变资源，不能并发写同一 optical/page texture。
- `EffectDisplayClock` 写死60。采用宿主显示器实际能力和当前活动预算；活跃交互可请求120，静态停钟；30fps内容与120Hz几何运动不要求相机/SCK也跑120。[C14]
- `EffectSession.holdsLastFrame` 当前仍每帧读取源并 tick。对已观察呈现且无等待回执的冻结态停止不需要的渲染时钟/捕获，改为传感器或状态事件唤醒。超时和撤销另有单次截止，不能因为停钟而失去故障检测。
- 无内容时不保留为演示服务的全屏截图流；可见 live preview 仍必须真实更新。
- GPU readback 只给明确诊断；不要把正常实时帧转 CGImage 再上传 GPU。使用统一内存不等于转换和带宽免费。

M5 GPU Neural Accelerator 是 GPU 内的矩阵加速结构，和16核 ANE 不同。只有相应 ML/矩阵路径才可能受益；普通刘海变形不是有意义的神经网络任务。先用 Core ML/受支持框架取得可用模型与实测结果，再考虑 M5 专用 Metal tensor/MPP 优化分支。不要让 M5 新功能成为 A18 Pro/旧 Mac 启动依赖。[A01,A05]

### ANE：可测的后端选择与采集节流

`FaceObservationSource` 已对 Vision 支持的 main stage 指定 ANE。这个指定不等于完整管线只运行于 ANE，也不证明当前视频流可用。[C18]

采集先比较设备原生420f/420v与现有 BGRA，查询 availableVideoPixelFormatTypes，验证 Vision、范围、方向与颜色结果。BGRA 在非原生源上可能额外转换和增加带宽；若模型真的要求 BGRA，保留合理路径，不机械转换整个产品。[A06]

现有 `now-lastSample >= 0.125` 仅节流分析到最高8Hz，未设置实际摄像头帧率。根据支持的 activeFormat/videoSupportedFrameRateRanges 调整 activeVideoMinFrameDuration 和 Max；不要承诺所有摄像头都支持2fps。记录实际PTS间隔与丢帧原因。[A07]

建议初始实验档：未启用/停用时0采集0推理；明确启用的在场观察单独低频2–4Hz分析，真实采集选择硬件支持的较低档；主动头动/嘴部挑战24/30fps采集和足够的关键点分析，身份 embedding 独立节流。实际数值由动作时序和误识测试决定，不为热状态忽略活体证据。

每个可交付模型比较 `.all`、`.cpuAndNeuralEngine`、`.cpuAndGPU`，cpuOnly只作可控基线/允许场景回退。cpuAndNeuralEngine允许CPU+ANE且排除GPU，没有“强制纯ANE”语义。比较同一模型、相同预处理、batch1、固定小输入尺寸下的冷加载、p50/p95、整机增量能量和错误率。使用Xcode/Core ML性能报告与可用的MLComputePlan检查实际设备分配；支持某单元不等于实际每层都在该单元。[A03,A09]

模型按功能生命周期加载，用户启动实验/功能后才预热，不每帧加载，也不登录后把未来功能所有模型常驻。降精度或换模型必须重新校准，不静默换不同 embedding 后端继续用旧模板。

## 4. A18 Pro 与 M5 的差异化验收

MacBook Neo 的 A18 Pro 是6核CPU（2P+4E）、5核GPU、16核ANE、60GB/s带宽、8GB统一内存。这里按实际Mac配置讨论，不能照抄手机端的GPU核心数。完整10核M5示例是4P+6E、10核GPU、16核ANE、153GB/s；具体机型和裁剪规格运行时读取。[A01,A02]

A18 Pro 优先解决常驻开销、缓存、模型加载、4K外接下的带宽和相机并行。可以给可丢弃缩略图/派生纹理缓存一个较小预算作为起点，但恢复日志和唯一必要恢复图片不参与任意逐出。M5的更大余量用于高刷新和多窗口，不用于永久跑满三类计算单元。

另一个功能差异：Neo 存在带和不带Touch ID的键盘配置，程序必须检查认证能力。现有 `AuthKeyPolicy` 明确要求 biometryCurrentSet，这条授权分支不能自动把系统密码当作等价指纹通过。保留Touch-ID-only策略；如为无Touch ID机器加入系统密码授权，需要显式不同策略/密钥版本与说明，在原AuthorizationService内完成并单独验收。不要靠去掉访问控制“兼容”。[C21,A02]

设置按 capability 驱动：屏幕刷新率、可用GPU族与API、统一内存、相机格式/帧率、Secure Enclave/Touch ID、真实盖角设备；不要只判断型号字符串。基础窗口操作、快捷键和无刘海胶囊应在两个平台都可用。盖角传感器、触觉反馈和安全认证能力不存在时给对应替代操作，不能模拟硬件数据。

热状态/低电量策略先降低装饰渲染、非前台预览和刷新频率，保留点击响应与恢复；主动验证无法在安全预算内完成时退出并说明使用系统确认，不能降低匹配门槛或用缓存成功补齐。

## 5. 真实性能门槛与测量方式

当前已提交数据：fold fast/no-animation热轮 first-change日志median182ms、strip353ms；冷轮634/812ms。glance单窗另次试验首张实时画面683ms、28frames/1s；不能和前一probe混成同一个场景。soak8s呈现35.9fps、capture-to-present P95 82.8ms、GPU P95 3.3ms。[C10,C22,C23]

这些数值支持先查采集、调度、主线程和WindowServer等待的路线，不能把两个P95相减当作CPU时间，更不能把无动画测试当作动效流畅证明。

### 完整测量序列

1. 固定 clean commit、工具链/SDK、OS构建、签名构建的二进制SHA256、配置开关、屏幕/缩放/FPS。不同源码运行的日志不可拼成同一验收。
2. 正式优化构建与诊断构建分开，先跑无高频日志版本，再查signpost；保持Swift6/strict/warnings-as-errors及既有优化配置。
3. 记录 input→proposalShown→preflight→captureStart→firstSample→preprocess→encode→GPUStart/End→drawablePresented→effectObserved。保留每次操作ID，使关键路径可关联。
4. 分开测 source完整帧、display ticks、提交数、真实呈现数、不同source帧数、丢弃原因；没有画面变化的低帧率不直接算掉帧。
5. 运行已存在的移动测试窗口：至少跨过10秒反转段，先60秒短测，再至少10分钟交互/30分钟相机与接收器稳态；睡眠/唤醒/热插拔/取消另测。
6. 功耗采用同屏亮度、相同外设与后台负载的基线/功能开启交替多轮。看本进程、WindowServer、coreaudiod等代办开销以及硬件可提供的整机或SoC功耗。不能将低CPU%当作低电量。
7. powermetrics只使用当前硬件/OS `--help`列出的sampler；没有ANE计数则标不可用，不能填0。不要解析私有寄存器制造不存在的功耗读数。
8. 后台在场模式与功能全关的基线分别测；摄像头绿灯、录音、显示器唤醒和进程子任务也进入验收。

### 首轮工程预算（拟议，不是Apple标准或当前成绩）

| 项目 | 首轮目标 | 失败后处理 |
|---|---|---|
| 功能全关、UI不展开、预热后10分钟 | app自建相机/录屏流0、推理0、渲染时钟0；不可丢的恢复/安全工作除外 | 逐模块消融，定位timer/回调，不仅改QoS |
| 空闲进程额外开销 | 平均CPU≤0.5%一个逻辑核，稳态主动唤醒目标<10/s；硬件事件例外单列 | 先重新测当前分支，不拿旧build16的4551/s当新值 |
| 主线程自有UI工作 | 60Hz单轮≤4ms，120Hz≤2ms；>50ms长任务逐个归因 | 将等待/预处理异步化，不能只缩短动画 |
| 主动操作反馈 | 已获权限、资源热态p95≤50ms显示真实进行中反馈 | 不显示未发生的完成 |
| 自有简单绘制场景 | 60/120Hz各自记录≥99%帧预算内；不能要求30fps源提供120张独立视频帧 | 掉帧同时记录主线程、GPU和drawable等待 |
| 资源释放 | 关闭后不再新采集/提交；原生stop成功后计数归零；异常停止可见且不自动续开 | 修生命周期，不只释放Swift引用 |
| 模型后端比较 | 相同准确率与攻击约束下比较p95和焦耳/有效尝试 | 不以低能耗换验证降级 |

未测得可靠绝对瓦数前不下整机功耗保证。基线噪声内的小改善如实写无显著差异。增加GPU队列深度、降低纹理分辨率、调整推理采样，每次只改变一项并记录功能退化。
