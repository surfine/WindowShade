# 检讨：理想 vs 现实

> 这一页回答一件事：**1.0.15（2026-09-26）之后 170 个提交、却 0 次发布，差在哪。**
> 每条差距都附可查的档案或指令；没查证的数不写；「源码存在」不写成「已做」。

## 0. 一句话

理想是 `blueprint.md` 的七条产品线一起走到能发布；现实是窗口这条线基本走完、其余六条只到「已进 App」，而这个人在等一个**一个人的验收漏斗**——每多开一条线，漏斗就多堵一件，没人从漏斗里拿走任何东西。

## 3. 差距的本质

要写得直接一点：

1. **瓶颈不是工程产能。** 代码量一直在涨（170 个提交），真正卡住的是**验收**：探针在有人用电脑时必须自己停下、Touch ID／配对／相机／真插拔显示器都等 Aaron 在场。工程这边一次能产出十条线的代码，验收这边一次只能过一件。
2. **范围比收敛快。** 每开一条新线（实时活动、电池、CarPlay、指挥、身份、隐私）都是往同一个漏斗里加东西，没有一次是从漏斗里拿走东西（删需求、砍范围、把线移出去）。1.0.16 的承诺因此一直在长，发布门槛一直在往后移。
3. **「本地已做」被当成了进度。** ledger 里那句「做成，不是本地已做」说的就是这件事：源码落地后没有紧跟一个「验过」或「发出」的动作，于是进度表看起来一直在前进，发布线一直没有动。
4. **发布不是一个动作，是一条没人负责的线。** 从 9/26 到现在，没有任何一次「打标签 → 发 Release → 部署官网 → 换日常 App」的完整循环跑通过一次。没有跑通过一次的事，第一次跑一定会踩坑；越晚跑，坑越多。

## 4. 过程检讨（自我批判）

这一节说的是流程问题，不是诚信问题。

| 现象 | 具体案例 | 性质 | 改法 |
| --- | --- | --- | --- |
| 「源码落地 → 宣称进度 → 事后更正」 | ⌥Tab 小程序那件一度写成「没做」（上一版这里写错，「选择窗口」那一半没错）；9/29 Aaron 定的四件事漏记、事后补记；10/1 起的一批工作一度误标「偏航」，10/3 更正 | 文档在事实之前先写结论，缺少「先落证据再改状态」的规矩 | 任何状态改动，先写可查命令或档案，再改那一格；写不出证据就保持「未验」 |
| 状态散落在多个 handoff，没有单一事实来源 | 漂移清单 [`tests/part10/DRIFT.md`](../../../tests/part10/DRIFT.md) 本身就记录了两轮「第一次漏登、门禁失败后补上」 | 同一事实在 blueprint / ledger / checklist / requirements-status / scorecard 各有一份，会互相不同步 | **复用既有 `v1.0.16` ledger**当唯一事实来源，不再新建一套（GPT-6 裁定 8；见 [LANDING.md](LANDING.md) 与 BRIEF 第 7 问） |
| 探针的绿没有保鲜期管理 | 10/2–3 改了刘海和看一眼，10/1 的绿就不再算数，但流程上没有自动标「失效」 | 代码改动与探针结果之间没有挂钩 | 探针结果绑定建构 sha；被改动覆盖的探针自动标「要重跑」 |
| 承诺范围只增不减 | 1.0.16 草稿承诺的功能集一路增长，没有一次公开砍掉 | 没有「移出到下一版」这个动作 | 每个版本明确写「砍了什么、为什么、移到哪」 |
| 同一事实前后自相矛盾 | 发布侧缺口一度在 README／BRIEF 写成「更新私钥未备份」，但 `DEVELOPMENT.md` 记「已有一份离线备份」；真正的缺口是恢复能力从没验过（GPT-6 审议时抓到） | 同一事实散落多处、没有对账 | 写缺口前先读回原始档案；发现矛盾当场更正并记进漂移账 |

**漂移清单现状**（供 GPT-6 参考）：`tests/part10/drift.json` 的 `code_map_drift` 共 33 条（含 W00 带进的四条），另有两条是路径映射（不是内容差异）。这条清单只解释「为什么和基线不一样」，不证明这些差异都对。
