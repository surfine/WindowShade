# WindowShade 2 前两部宣传片拆解：为什么僵硬

2026-10-18。对象是已发布的两部，按本机 4K 母带审：

| 代号 | B 站 | 标题 | 本机母带 | 规格 |
| --- | --- | --- | --- | --- |
| v14 | BV1T3Hk6HEGo | 我再也不会觉得 MacBook 上的刘海碍眼了 | `film/ws2-opus/out/gate/v14-4k.mp4` | 3840×2160，60 fps，53.80 s |
| d21 | BV1CtHx6vEhQ | 看一眼，点个头，Mac 就有了新玩法。 | `film/ws2-opus/out/future/gate/draft21-4k.mp4` | 3840×2160，30 fps，60.25 s |

源码在公开仓库 `film/ws2-opus/src`（v14：`timeline.ts`、`cut.ts`、`camera.ts`、`scene.ts`、`motion/*`；d21：`src/future/film/*`）。这份拆解只读，没有改它们。新片的概念与分镜在 `docs/design-drafts/WindowShade 2 宣传片 分镜.html`。

**结论**：两部的弹簧求解器本身没错（`motion/springs.ts` 的 `solve()` 换目标时保留位置和速度），僵硬来自**怎么用**：主体动时镜头必须停、镜头动时主体必须停；每一段运动都用临界阻尼收到零速度再停住；窗口沿直线等比缩小飞进刘海，刘海的“鼓一下”是另外打的一脚，不继承窗口的速度；段落按小节等分，交接靠剪或甩；意思靠一直挂在顶上的标题说。机器指标里 carry 看着合格（0.78 / 0.90），但静止率 0.758 / 0.651 和能量图说明片子大部分时间是死的，动的部分挤在几次甩镜里。

## 2. 僵硬的来源（按影响排序，每条带时间点与代码）

### F1 · v14：主体动时镜头被规定不许动（全片）

`src/camera.ts` 头注释：“收起、放回、島展開、窗口變形期間鏡頭停住。移動只發生在兩拍之間、主角動作已經停穩之後。”`busyUntil()` 对 `draw / say / lips / nod / drag / slots / peek` 直接返回 `s.end`，整镜锁死；其它镜在动作后再锁 0.7–1.15 s。镜头移动只在两镜之间的间隙里，用 `dolly`（response 1.6 s、ζ 1）走完。结果是“主体在死画面里动，然后画面绕着死主体动”的停—走—停，正是 doctrine §1 的“没有相机”与“入场即停”。例：2.0–4.9 s 收进刘海这一镜，窗口飞行期间镜头一帧不动；镜头只在 17.7、22.6、35.4 s 这类换景别的刀口前后才走。

### F2 · v14：窗口飞进刘海是直线 + 等比缩小 + 临界阻尼，刘海的回应是另打一脚（≈2.3–2.7 s）

`src/scene.ts:81` `tucked()`：中心点 `mix(cx, 50, p)`、`mix(cy, 3, p)` 走直线，`scale = mix(1, 7 / r.w, p)` 等比缩，圆角线性收。进度 `tuckProgress()` 用 `settle`（0.38 s，ζ 1，`motion/site.ts:106`），收到终点没有过冲、没有跟随。刘海的鼓起是 `TUCK_KICK` 常量（700×K、300×K px/s）在 `TUCK_COVER` 那一帧打进去，与窗口到达时的真实速度无关。看起来是“窗口消失 + 刘海自己抖了一下”，而不是“刘海接住了一个有重量的东西”。macOS 的窗口收起（genie / scale 动画）宽度先收、高度后收，路径是弧线。

### F3 · v14：76 % 的画面是静止的，最长 5.53 s（22.90–28.43 s）

那是 `say` 镜（`cut.ts`：拍 46–58，“说一句，草稿发出，文章改三处”）：中景、镜头锁死（F1），画面上唯一的动作是文字在草稿里改三处，字小到 1080p 下读不清。随后 `lips`（28.5–32.5 s）同样是中景锁死。doctrine §2 要求静止 ≥25 %，但这里的静止不是“落定后的呼吸”，是“没有东西可看”。

### F4 · v14：标题带挂满全片，相机为它让路（0–53 s 全程）

`cut.ts` 的 `CAPTIONS` 每段一句、从这段第一刀进、最后一刀出，合起来覆盖全片；`camera.ts` 的 `clearTitle()` 每一帧把机身往下推，保证银边在标题带下面。标题 66 px 中文 + 30 px 英文（英文低于 doctrine 辅助字 32 px 的线）。于是取景服从文字，不服从主体：中景下刘海只有约 180×32 px，从来不是画面主角（doctrine §5：主角 ≥ 170 px 且占内容高 1/3）。意思是标题说的，不是画面演的。

### F5 · v14：每一刀都跳母带时间，屏幕状态瞬移（17 刀，最明显 17.68、22.62 s）

`cut.ts` 从 169 s 母带按 1:1 取 17 段、“每一刀都换景别”。相机在刀口前后用 dolly 软化取景，但屏幕里的指针、窗口位置、刘海状态在刀口直接跳到另一段母带。carry_flow 在 17.68 s（`slots`→`draw`，中景→带手机的整机）判裸切，存活点 0/800；22.62 s（`draw`→`say`）存活 6/800。能量没断，但“同一个东西”断了。

### F6 · d21：每次换机器都是一次没走完的甩镜，到下一个键时位置跳 10–16 %

`src/future/film/shot.ts` 两台机器 `SEAT` 中心相距 0.56 m；`shotAt()` 在相邻键之间走 `dolly()`，response 固定 1.6 s，**不看两个键隔多久**。换机的几段间隔只有 0.83–1.0 s：

| 区间 | 时长 | 走到 | 下一个键处的位置跳变 |
| --- | --- | --- | --- |
| 11.83→12.67 s（Neo→Air） | 0.83 s | 84 % | **16 %** |
| 17.67→18.67 s（Air→Neo） | 1.00 s | 90 % | 10 % |
| 29.67→30.67 s（Neo→Air） | 1.00 s | 90 % | 10 % |
| 33.33→34.33 s（推近岛） | 1.00 s | 90 % | 10 % |
| 48.33→49.33 s（Neo→Air） | 1.00 s | 90 % | 10 % |
| 54.98→55.00 s（双机） | 0.02 s | 0 % | **100 %，硬切** |

carry_flow 把 12.28、30.10、37.37、48.68 s 都判成“承接”，但存活点都是 0/800：那是甩镜的运动在撑分数，不是同一个东西活下来。18.22 s 直接是裸边界。

### F7 · d21：两台机器摆得太近，甩镜时一台的盖子横切另一台的屏幕（12.17–12.43 s，18、30、37 s 同法）

逐帧看 11.5–13.1 s：中段三帧里 Neo 和 Air 的盖子在画面中间相互遮挡，形成一条笔直的竖缝，读起来像分屏擦除，不像镜头在桌上移动。原因同 F6：0.56 m 的间距对 30° FOV 的机位太近，甩过去时前景机身扫过画面。

### F8 · d21：开场 7.5 s 是一块锁屏，解锁靠字幕说（1.7–9.3 s）

`cues.ts`：`T.wake 100`、`faceOn 400`、`faceOk 445`、`unlock 555`（60 fps 帧号）。这段相机只在 `dist 0.56→0.54→0.52→0.58` 之间缓慢挪动，像素在动所以没被 still 腿抓到，但观感是死的（doctrine §4：静止段必须真静止，不给静物加漂浮）。“看一眼”这个动作在画面上从来没有发生：没有脸、没有视线、没有摄像头的反应，只有打字机字幕“你一看，Mac 就解锁”（`LINES[0]`，0.6–8.3 s）。片名承诺的“看一眼”在第一镜就交给了文字。

### F9 · 两部：刘海一展开，肩就先收到 0 再长回来（每次 alert / ask / drop / digest）

`motion/site.ts` `ISLAND_SHAPES` 里 `alert`、`shelf`、`drop`、`ask`、`digest` 都写 `rs: 0`。从 compact 走到这些形状时，肩半径和宽、高、底角挂在同一根弹簧上一起插值到 0，所以每次开口顶角都先变成直角、收回时再长出肩。本机实测刘海的肩延伸 7.12 pt，是屏幕顶边和刘海竖边之间的连续曲率过渡，展开不该丢掉它（同一问题在 `docs/design-drafts/宽形状画肩.html` 里已经单独提过）。

### F10 · 两部：屏幕里的 macOS 是 HTML 画的，并且是一张平的视频贴图

v14 的桌面、终端、草稿在 `src/parts/Mock.tsx` 手搓；d21 先把 `Screen.tsx` 渲成 `public/future/plates/{air,neo}.mp4`，再作为 `useOffthreadVideoTexture` 贴到 glb 屏幕上（`stage.tsx:549`）。这违反本机规则 1（产品界面必须是真实运行画面），也就是 Aaron 说的“UI 像山寨”。另一个后果：窗口、刘海、壁纸都在同一张贴图里，相机一动，界面没有任何层次，岛和窗口不会相对屏幕产生视差。

### F11 · d21：段落按小节等分，交接全落在小节线（12、18、30、38、48 s）

`cues.ts` `SEGS`：720/360/720/480/600/420/300 帧，`HANDS = [720, 1080, 1800, 2280, 2880]`。CV 0.30，所有换段都卡在 120 帧的小节线上，节拍器感强。卡拍应该卡时机，不该让所有段落长度都是小节的整数倍。

### F12 · 两部：字幕偏小，d21 用打字机

d21 字幕 `H × 0.042` = 45 px（1080p），低于 doctrine 字幕 56 px 的线，且逐字打出（`CHAR_RATE = 4` 帧一个字），读者要等字。v14 英文副标 30 px。

## 3. 真正做对了、新片要保留的

| 保留 | 出处 | 为什么 |
| --- | --- | --- |
| 弹簧求解器换目标保留位置和速度 | `motion/springs.ts` `solve()`、`approach()` | 这是速度交接的基础，新片直接用，只是改参数和用法 |
| 设计稿的命名弹簧表 | `springs.ts` `SPRING`（calm / expand / bloom / catch / flyOut …） | 与设计稿一致，新片的刘海仍用这张表；只有窗口飞行与相机改用欠阻尼 |
| 内容在形状走到 40 % 时进、退场先于形状 0.04 s | `motion/direction.ts` `CONTENT_AT`、`EXIT_GAP` | 这是 Apple 式的分层，留下 |
| 起因确定的那一帧再动 | `timeline.ts` `IslandEvent.at` 的注释 | 因果顺序对；但把外部事件前的 1.1 s 等待（`BEAT`）在片子里缩到 0.3 s 以内 |
| 真机模型与量过的刘海 | USDZ→glb 的 15 英寸 Air、`notchPath.ts` 从网格拟合 | 机身不再“失真”的前提，新片沿用 glb 与 `stage.tsx` 的光照 |
| 一个共享刘海贯穿全片 | concept `REVIEW.md`、v14 全片 | 新片把它推到极致：刘海就是转场 |
| d21 的“同一个世界”思路 | `shot.ts`：两台机器在同一张桌上，相机走过去 | 方向对，执行错（F6、F7）；新片用一台机器 + 连续相机 |
| 问题先说 | v14 开场“窗口太多，桌面挤满了” | 钩子要更快（≤1.5 s 见到刘海吃掉窗口），但先说痛点的顺序保留 |
| 节拍网格先测后用 | `music.ts`：122 BPM，残差 3.8 ms | 新片同样先测；只用来卡时机 |
| 4K 分块渲染与等长 PTS 拼接 | `handoff/RENDER-4K.md`、`scripts/concat-equal-pts.sh` | `--gl=angle` + 分块，加 VideoToolbox 编码，之前快约 4× |
| 短文案 | `copy-guide.md`，≤12 字 | 保留，但数量砍到 6 句以内，只在画面说不清时出现 |

## 4. 给新片的反向规则（由上面推出）

1. 主体动时相机也在动：落后主体 0.1 s 跟随，或提前到主体将到之处；只有 rest 拍真静止。（反 F1）
2. 飞行物走弧线、宽高分别收、欠阻尼过冲 2–4 %；刘海接住时继承它的到达速度。（反 F2）
3. 静止只放在“落定之后”，每次 0.6–1.2 s，不出现 >3 s 的静止；静止率 0.25–0.45。（反 F3、F8）
4. 不挂常驻标题带；字幕总数 ≤ 6 句、≥ 56 px，只在概念段出现。（反 F4、F12）
5. 一镜到底，不跳母带时间；边界写明哪个东西活下来。（反 F5、F6、F7）
6. 展开时肩保留，形状四个参数各自有弹簧但同一时刻起步。（反 F9）
7. 已有功能用真实录屏贴进 3D 屏幕且分层（壁纸、窗口、刘海三层），没有的功能做成明确的抽象段。（反 F10）
8. 段落长度不按小节等分；只把关键动作的落点卡在拍上。（反 F11）
