# WindowShade 宣传片：制作与验收 playbook

这份文件是给下一个接手模型看的。它不是灵感清单，是这个项目踩过的坑和已经量过的数。
**先读完再动画面。** 很多"看起来要重做"的问题，根因只有一行坐标或一个 CSS 层叠。

## 0. 开工前

1. 读 [`../README.md`](../README.md)（结构、时间表、命令）、`src/timeline.ts`（唯一的提示表）和本文件。
2. 读产品源码，不凭印象：刘海行为在 `prototype/App/Notch.swift`，弹簧令牌在 `prototype/Core/FlickMotion.swift`，设置页行名照真实界面。
3. 复用这支片已经成立的语言：浅色桌面、代码合成的 D 大调 120bpm、同一套 spring 令牌、同一套窗口尺寸。
   **不要另起一种风格**，也不要把"新功能联播"当成宣传片。
4. 一次只改一个缺陷。先出一帧静帧对齐，再扫一段，再全片。全片渲染是最后一步，不是检查手段。

## 1. 渲染：先量，再渲

```bash
npm run audio
node scripts/render.mjs out/windowshade-1.0.18-promo.mp4 2 Promo
node scripts/render.mjs out/windowshade-1.0.18-vertical.mp4 1 PromoVertical
```

- **GPU 加速在画帧，不在编码。** 脚本已固定 `chromiumOptions: { gl: "angle" }`（Chrome 的 ANGLE/Metal 后端）。
  实测（四张毛玻璃卡、4K、120 帧）：软件光栅 63.7s → 18.7s（3.4×），x264 crf 16 与文件大小不变，
  整段 PSNR 51.8 dB / SSIM 0.9988。基准可复跑：`node scripts/bench-gpu.mjs`。
- **不要用 `hardwareAcceleration`（VideoToolbox）当提速手段**：同段实测 43.9s，比 ANGLE 慢，且码率翻倍。
  它只加速 H.264 编码，而瓶颈是 Chromium 逐帧绘制 4K（毛玻璃、阴影、大圆角）。
- **改过画面源码后，先删旧分块再重渲**：`rm -rf out/.chunks-Promo out/.chunks-PromoVertical`。
  脚本会"断点续渲"，复用同名旧块——内容改了但块还在，会得到一支新旧混合的片子。
- 渲染按 480 帧一块，最后无损拼接再配 `public/soundtrack.wav`。4K 单块约 3 分钟（GL 路径），竖版更快。
- 音频响度用 `loudnorm` 复测：当前母带约 −17.2 LUFS、真峰 −1.0 dBTP。
  **不要为了凑 −14 LUFS 直接加增益**，峰值已经贴限，会削顶；要改就重做母带。

## 2. 审片：用成片，不用感觉

用户报「第几秒不对」时：

```bash
ffmpeg -ss 38 -i <成片>.mp4 -frames:v 1 -vf scale=1920:1080 /tmp/check38.png
```

**从最终 mp4 抽帧**，不要拿 `stills.mjs` 的渲染帧代替；也不要用半比例图判断排版。

改一段动效时的固定动作：

1. 以 **10 帧**步长扫过整段（60fps 下 6 帧 = 0.1s），横竖两版都扫。
2. 只看**稳态帧**不够，交接帧才是事故现场：元素进出、z-order 切换、字幕换行、抽屉开合。
3. 构图用坐标表算：中心、左右留白、上下间距、两个元素是否重叠。不要"看着差不多"。
4. 全分辨率看一次文字边缘和阴影。半比例会把"被裁掉的阴影"和"没渲染出来的元素"都糊掉。

判据：

- **文字被动作穿过**：先改路径或改字幕位置，不要指望 z-index 让文字"能读"就算过——能读不等于不脏。
- **同一元素两处渲染**：飞行副本和桌面原件、抽屉预览和飞出窗口，交接时必须只剩一个。
- **流畅**：一个属性只走一条命名弹簧；不要混 `pop`/`tw`/线性。回弹只用在产品本身会回弹的方向。
- **签名音只出现一次**：grep 提示表里的 cue，别让 chime 在提醒、标题、片尾各响一次。

## 3. 已知根因案例（照这个顺序查）

1. **缩得越小、偏得越右**（图1 事件）：`transformOrigin: "50% 0%"` 与手写的
   `translateX(+w/2) scale(s) translateX(-w/2)` 是两套居中，叠加后中心偏移 `(1-s)·w/2`；
   s=0.3 时右偏 168px。修法：只留一套——原点半上 + 纯 `scale()`。
2. **元素"没渲染"**（1.0.18 徽标）：`Rise` 内层的 `filter` 会让绝对定位子元素的包含块变成内层，
   外层的 `overflow: hidden` 于是把它裁掉。修法：定位容器放 `Rise` **外面**，`Rise` 只包内容本身。
3. **飞进刘海悬在下面**：产品是 `NotchIsland.tuckTarget`——快照**沿宽高压进刘海矩形**，不是等比缩成 0.3。
   修法：宽高都插值到胶囊的实时矩形，终点与胶囊重合、被盖住；飞入 `settle`（不回弹），取出 `flyOut`（带回弹）。
4. **取出时双影**：抽屉预览与飞行窗口同时在场。修法：起飞前 2–5 帧把预览清掉，抽屉壳随后收合。
5. **字幕与飞行路径相撞**：动作沿画面中轴飞，顶部标题带必被穿过。修法：这一段字幕下移到底部，
   给刘海和窗口让出整块中段。
6. **飞行窗口顶角有直角切口**：飞行容器 `overflow: hidden` 裁掉了子元素阴影。
   只缩放、尺寸已精确匹配时不需要裁剪，去掉即可。
7. **设置窗口显得空、偏**：窗口居中（横版 1180 宽时 x=370），高度收到内容量级；
   底部 150px 死白会让整扇窗显得没做完。

## 4. 不要这样做

- 不要为验证一个小改动跑一次 20 分钟全片渲染。
- 不要在全片渲染中途改源码后继续跑旧分块。
- 不要把"GPU"理解成硬件编码；先看瓶颈是画帧还是编码。
- 不要用一张静帧宣布动效没问题；动效缺陷都在帧与帧之间。
- 不要在没扫交接帧的情况下说"流畅"。
- 不要为修画面去改声音、改时间表。
- 不要新增一套视觉语言；这支片的语言已经成立。
